Capitolo 01 · Fondamenti

Introduzione allo sviluppo mobile e Android

In breve: Android ≈ 70–74% del mercato, iOS il resto. Nativo = massime performance; cross-platform = un codice per tutto, con compromessi. L'app è fatta di 4 componenti, si compila in APK via DEX e gira su ART.

Mercato e bivio architetturale

Sviluppo nativo

Codice specifico per piattaforma (Kotlin/Java per Android, Swift/Objective-C per iOS). Massime performance e accesso immediato alle API del dispositivo.

Sviluppo cross-platform

Un codice, più piattaforme. Costi e tempi minori, possibili compromessi su prestazioni e ritardi nel supporto alle nuove API.

  • React Native (Meta): basato su JavaScript.
  • Flutter (Google): basato su Dart, rendering custom (non usa le UI native, le ridisegna).
  • Kotlin Multiplatform Mobile — KMM (JetBrains): non è un framework UI ma un SDK: condivide la logica di business in Kotlin, UI resta nativa.

I 4 componenti core

  1. Activities — singole schermate con UI.
  2. Services — operazioni lunghe in background, senza UI (musica, download).
  3. Broadcast Receivers — reagiscono a eventi di sistema (batteria scarica, sblocco).
  4. Content Providers — condividono dati tra app in modo sicuro (contatti).

Il Modern Android Development usa le librerie Jetpack (ViewModel, WorkManager, Room) per gestire il ciclo di vita di questi componenti.

Gradle, APK, DEX e ART

  • Android Studio (IDE ufficiale su IntelliJ, dal 2015 dopo Eclipse).
  • Gradle: build automation open-source su concetti Ant/Maven, con DSL Groovy/Kotlin.
  • ARM big.LITTLE: nuclei di dimensioni diverse per prestazioni ed efficienza energetica.
  1. Sorgente Kotlin/Java → bytecode .class.
  2. .class → formato DEX (Dalvik Executable) ottimizzato per mobile.
  3. aapt unisce DEX + risorse → archivio APK.

ART vs Dalvik

Dalvik usava compilazione JIT (Just In Time). ART compila in codice nativo all'installazione (AOT, Ahead-Of-Time): esecuzione più veloce, installazione più lunga e più spazio occupato.

UX, UI e Figma

UX (User Experience)

Struttura logica, gerarchie, flussi funzionali. Analizza i comportamenti reali degli utenti.

UI (User Interface)

Struttura visiva: colori, font, icone. Rende il prodotto visivamente stimolante.

Figma nei quiz: piattaforma cloud (WebGL/WASM), CRDT + WebSocket per il real-time senza conflitti (Last-Writer-Wins), veri prototipi prima del codice. Motore in C++ transpilato in WebAssembly. A differenza di Sketch, niente installazioni né file locali.

AndroidManifest.xml

Nella root del progetto. Dichiara package name (ID univoco), tutti i componenti (senza dichiarazione → crash all'avvio), permessi (uses-permission) e feature hardware.

Activity Home nel Manifest
<activity android:name=".MainActivity" android:exported="true">
    <intent-filter>
        <action android:name="android.intent.action.MAIN" />
        <category android:name="android.intent.category.LAUNCHER" />
    </intent-filter>
</activity>

Punto chiave: android:exported="true" = avviabile anche da app esterne, incluso il launcher di sistema.

Capitolo 02 · Il linguaggio

Il linguaggio Kotlin

In breve: tutto è oggetto, niente conversioni implicite. val = sola lettura, var = mutabile. I null si gestiscono con ?., ?: e !!.

Null safety

String? può essere null. Safe call ?. ritorna null se null; Elvis ?: dà un default; !! forza e rischia il crash (NullPointerException).

Conversioni

Niente assegnazioni implicite: serve .toLong() per passare da Int a Long.

Classi e ordine di inizializzazione

  1. Costruttore primario nella firma (se assente, Kotlin ne crea uno vuoto).
  2. Proprietà e blocchi init dall'alto verso il basso, in ordine di apparizione. init non è un costruttore: valida (es. require(prezzo >= 0)).
  3. Costruttore secondario (constructor), per ultimo.
Regola d'oro (quiz): il secondario deve delegare al primario con : this(...), altrimenti errore di compilazione.

Lambda e collezioni

Lambda, filter e it
val numeri = listOf(3, 8, 12, 5)
val maggiori7 = numeri.filter { n -> n > 7 }
val compatta = numeri.filter { it > 7 }
Funzioni viste nei quiz: zip (unisce due collezioni in Pair, es. distanza di Hamming), count { } (quanti soddisfano la condizione), map { } (trasforma in nuova lista).
Higher-Order Function (quiz calcolatrice)
fun calcola(a: Int, b: Int, operazione: (Int, Int) -> Int): Int {
    return operazione(a, b)
}
fun main() {
    val risultato = calcola(6, 3) { x, y -> x * y }
    println(risultato) // 18
}

Capitolo 03 · Risorse

Gestione delle risorse e UI

In breve: codice separato dalle risorse. A 160 dpi 1 dp = 1 px; i testi usano SP. I qualificatori scelgono il layout giusto a runtime.

Cartella res/ e R.java
CartellaContenuto
layout/XML delle interfacce
values/stringhe, colori, dimensioni, stili
drawable/immagini, vettori, shape XML
mipmap/solo icone launcher

A build time aapt assegna ID esadecimali (es. 0x7f05000b) nella classe R.java: da XML @tipo/nome, da codice R.tipo.nome.

Laboratorio 1 — DP, pixel e pollici

Risoluzione = pixel totali; density (DPI) = pixel per pollice. Baseline mdpi = 160 dpi. Formule: px = dp × (dpi / 160) e pollici = px / dpi.

I testi usano SP: come i DP ma scalano con le preferenze font del sistema.

Qualificatori e stili

  • res/layout/ default portrait, res/layout-land/ per la rotazione, res/values-en/ per l'inglese. Sintassi: <risorsa>-<qualificatore>, con fallback al default.
  • Style → singola View (style="@style/MioStile"). Theme → intera app/Activity dal Manifest (android:theme="@style/MioTema"), tocca anche status bar e colori primari. Entrambi con parent.

Capitolo 04 · Componenti

Activity, Intent e ciclo di vita

In breve: l'Activity è una schermata; gli Intent sono messaggi espliciti o impliciti. I risultati si chiedono con Contract → Register → Launch. La rotazione distrugge e ricrea: lo stato va nel ViewModel.

Intent espliciti

Classe esatta (ActivityB::class.java). Quasi sempre dentro la propria app.

Intent impliciti

Azione generica (ACTION_VIEW) + dati. Il sistema sceglie tra gli intent-filter installati.

Esempi di Intent
// 1. Esplicito
val intentEsplicito = Intent(this, SecondActivity::class.java)
startActivity(intentEsplicito)

// 2. Implicito (web)
val uri = Uri.parse("http://www.uninsubria.it")
startActivity(Intent(Intent.ACTION_VIEW, uri))
Attenzione all'esame: startActivityForResult() + onActivityResult() sono deprecati: se il sistema uccideva l'app in background, il risultato si perdeva.
Activity Result API (da quiz)
val launcher = registerForActivityResult(
    ActivityResultContracts.StartActivityForResult()
) { result ->
    if (result.resultCode == Activity.RESULT_OK) {
        val data = result.data?.getStringExtra("RISPOSTA")
    }
}
button.setOnClickListener {
    launcher.launch(Intent(this, SecondActivity::class.java))
}

Laboratorio 2 — Ciclo di vita (tocca uno stato)

Seleziona un callback: onCreate (setup iniziale con setContentView) → onStart (visibile) → onResume (focus) → onPause (no focus) → onStop (nascosta) → onDestroy. Ritorni in foreground con frecce tratteggiate; Foreground lifetime = Resume↔Pause, Visible lifetime = Start↔Stop.

Configuration changes, Task e Back Stack

  1. ViewModel (MVVM): sopravvive alle rotazioni, tiene lo stato UI. Approccio moderno standard.
  2. onSaveInstanceState / onRestoreInstanceState: Bundle chiave-valore alla ricreazione.
  3. Manifest (configChanges): evita il restart chiamando onConfigurationChanged, ma è sconsigliato.
  • Task = insieme di Activity per un lavoro, in Back Stack LIFO. Back = pop + onResume() della precedente.
  • FLAG_ACTIVITY_NEW_TASK: nuovo task o porta in primo piano. CLEAR_TASK (spesso con NEW_TASK, es. dopo logout): svuota il task, la nuova è root e Back esce dall'app.

Capitolo 05 · Liste

UI e liste: da ListView a Compose

In breve: View + ViewGroup = pattern Composite. Le liste riciclano le righe (convertView / ViewHolder). In Compose le liste sono LazyColumn.

  • View (Component, con onDraw()) e ViewGroup (Composite contenitore).
  • LinearLayout: riga/colonna con layout_weight per lo spazio extra. ConstraintLayout: flat con vincoli, performante. FrameLayout: sovrappone i figli (cornice).
  • Adapter = ponte dati ↔ ListView (ArrayAdapter, CursorAdapter, BaseAdapter).

Laboratorio 3 — View recycling

Creare oggetti costa (GC). La ListView tiene in RAM solo le righe visibili + scorta: chi esce va nello Scrap e rientra come convertView in getView(position, convertView, parent).

SimpleAdapter vs ArrayAdapter

ArrayAdapter = lista semplice. SimpleAdapter = Map (List<Map<String, Any>>) con più campi per riga (titolo + sottotitolo + immagine); gli array sono chiavi e ID view. Le immagini da URL vogliono ViewBinder + Glide.

RecyclerView

Layout delegato ai LayoutManager (Linear/Grid), ViewHolder imposto per architettura: riciclo efficientissimo.

XML → Compose: Linear vertical → Column, horizontal → Row, FrameLayout → Box, RecyclerView → LazyColumn/LazyRow, setOnItemClickListener → Modifier.clickable.
Lista in Compose + Coil
@Composable
fun ListaUtenti(utenti: List<String>) {
    LazyColumn {
        items(utenti) { utente ->
            Text(utente, modifier = Modifier.fillMaxWidth().padding(16.dp))
        }
    }
}
// Immagini da rete senza bloccare la UI (serve permesso INTERNET)
@Composable fun Cover() {
    AsyncImage(model = "https://picsum.photos/200/300",
        contentDescription = "Prova", modifier = Modifier.size(64.dp))
}

Capitolo 06 · Navigazione classica

Fragments e Navigation Component

In breve: il Fragment è una porzione di UI riusabile, sempre dentro un'Activity. La UI nasce in onCreateView con inflate; si naviga con NavGraph + NavHost + NavController.

  • Host visivo = FragmentContainerView. UI creata in onCreateView() con inflate() che deve ritornare la View.
  • Vantaggi: modularità, riusabilità (es. menù laterale), adattabilità (master-detail su tablet).
Nota per l'esame: un Fragment non esiste da solo: vive dentro un'Activity e ne segue il ciclo di vita. Attenzione a onDestroyView() (view distrutta, Fragment vivo nel backstack) vs onDestroy().
  1. onAttach → assegnato all'Activity.
  2. onCreate → inizializzazione Fragment.
  3. onCreateView → inflate della gerarchia.
  4. onActivityCreated / onStart / onResume → visibile e attivo.
  5. onPause / onStop → onDestroyView → onDestroy → onDetach → dal backstack si torna a onCreateView.
Fragment + navigazione vecchia e nuova
class ExampleFragment : Fragment() {
    override fun onCreateView(inflater: LayoutInflater, c: ViewGroup?, s: Bundle?): View? =
        inflater.inflate(R.layout.fragment_example, c, false)
}
// Vecchio (verboso, sconsigliato)
supportFragmentManager.beginTransaction()
    .replace(R.id.fragmentContainerView, DetailFragment())
    .addToBackStack(null).commit()
// Nuovo: NavController (lo swap + backstack li fa lui)
button.setOnClickListener {
    findNavController().navigate(R.id.action_homeFragment_to_detailFragment)
}
Domanda tipica: chi fa lo swap e il backstack? Il NavController. NavHost = contenitore, NavGraph (res/navigation) = mappa di destinazioni e azioni.

Laboratorio 4 — Stato e ricomposizione

Ciclo: State → UI → Event → State. Senza mutableStateOf + remember, la UI non si aggiorna e la variabile si re-inizializza a ogni refresh.

0

Ricomposizioni: 0

Counter corretto + liste + navigazione
@Composable
fun Counter() {
    var count by remember { mutableStateOf(0) }
    Button(onClick = { count++ }) { Text("Click: $count") }
}
@Composable
fun UserListScreen(users: List<String>) {
    LazyColumn { items(users) { u -> Text("Utente: $u", Modifier.padding(8.dp)) } }
}
// Navigazione: rememberNavController + NavHost + composable("rotta")
@Composable
fun AppNavigation() {
    val nav = rememberNavController()
    NavHost(nav, startDestination = "home") {
        composable("home") { HomeScreen({ nav.navigate("detail") }) }
        composable("detail") { DetailScreen() }
    }
}

Side effects: il codice asincrono nel corpo del Composable si rieseguirebbe a ogni ricomposizione → usare LaunchedEffect (una volta all'ingresso o al cambio key) con withContext(Dispatchers.IO). Immagini: Coil AsyncImage (download async + cache, senza bloccare la UI).

Capitolo 08 · Background

Esecuzione in background: Services e alternative

In breve: il Service non ha UI e gira nel Main Thread. Immediato ed evidente → Foreground Service; differibile → WorkManager.

Trabocchetto: il Service non crea un thread da solo. Rete e calcoli pesanti vogliono thread/coroutine, altrimenti ANR.
  1. Background Service: invisibile (compressione storage). Da API 26 limitatissimo → oggi WorkManager.
  2. Foreground Service: evidente (musica, GPS). Notifica obbligatoria.
  3. Bound Service: client-server via IBinder, vive finché c'è un client.

Started

startService() → onCreate → onStartCommand (gira indefinitamente) → stopService/stopSelf → onDestroy.

Bound

bindService() → onCreate → onBind (ritorna IBinder) → unbindService → onDestroy.

Foreground music player
// Manifest: permesso FOREGROUND_SERVICE + tipo (es. mediaPlayback)
class MusicForegroundService : Service() {
    override fun onStartCommand(i: Intent?, f: Int, s: Int): Int {
        startForeground(1, createNotification())
        mediaPlayer?.start()
        return START_STICKY // ucciso per RAM -> riavviato con intent nullo
    }
    override fun onBind(i: Intent?): IBinder? = null
}

START_STICKY = ricrea da solo; START_NOT_STICKY = no, salvo intent in coda. Il Bound usa ServiceConnection per chiamare metodi come musicService.pause().

Laboratorio 5 — Quale soluzione?

Seleziona uno scenario per la raccomandazione architetturale.

  • WorkManager: garantisce il lavoro anche ad app chiusa o dopo riavvio, rispetta batteria (Doze, App Standby) e Constraints (Wi-Fi + carica).
  • Broadcast Receiver: senza UI, reagisce a broadcast (Wi-Fi, batteria). Da Manifest o registerReceiver.
  • Content Provider: condivide dati tra app (contatti, galleria).

Capitolo 09 · Dati

Persistenza dei dati: Room e Firebase

In breve: impostazioni → DataStore; file → media; dati strutturati locali → Room; dati condivisi → Firebase. Room verifica le query a compile-time; i NoSQL si denormalizzano.

  • SharedPreferences / DataStore: chiave-valore (impostazioni, token).
  • SQLite embedded: libreria C compatta, nessun server, Type Affinity rilassato. Storico: SQLiteOpenHelper (onCreate/onUpgrade) + SQL manuali + ContentValues/Cursor → verboso e non type-safe.

Room: Entity, DAO, Database

  1. Entity (@Entity): data class = tabella.
  2. DAO (@Dao): query. suspend = va in coroutine; Flow = stream reattivo nel tempo.
  3. Database (@Database): contenitore astratto, check a compile-time.

Catena: UI Compose → ViewModel (raccoglie il Flow) → Repository (astrae) → DAO (oggetti→SQL) → SQLite su disco. Senza KSP (ksp(androidx.room.compiler) nel Gradle) il progetto non compila: è lui a generare il codice SQLite.

I tre componenti di Room
@Entity(tableName = "shopping_items")
data class ShoppingItem(
    @PrimaryKey(autoGenerate = true) val id: Int = 0,
    val name: String, val quantity: Int
)
@Dao
interface ShoppingDao {
    @Query("SELECT * FROM shopping_items")
    fun getAllItems(): Flow<List<ShoppingItem>>
    @Insert
    suspend fun insertItem(item: ShoppingItem)
}
@Database(entities = [ShoppingItem::class], version = 1)
abstract class AppDatabase : RoomDatabase() {
    abstract fun shoppingDao(): ShoppingDao
}
// UI reattiva: collectAsStateWithLifecycle() converte Flow -> State -> ricomposizione (niente notifyDataSetChanged)
